# corpus-ledger — the third copy of the authored corpus

**If eligibility gates have been destroyed by a sync, this is where they come
back from. Skip to "Restoring" below.**

## Why this exists

The instrument half of the corpus — the funds, their sources, their encoded
eligibility gates and clauses, and how a founder applies — is *authored*, by a
person and by encoding runs on a workstation. It cannot be regenerated by
re-running an extractor. It lived in exactly two places: `data/db.sqlite`,
which is gitignored because it is 645 MB, and whatever had been promoted to the
corpus of record on the Railway volume.

On **2026-08-11** those two disagreed by **1,070 eligibility gates** — 7,471 on
the workstation and in Postgres, 6,401 on the volume. The channels between the
stores move the whole file with `--overwrite`. There was no third copy, and
nothing in the repository could make one.

This is the third copy. It is text, it is committed, it diffs in review, and it
restores.

## What is in here, and what is not

| file | rows at first export | what it holds |
|---|---|---|
| `funding_instruments.jsonl` | 1,088 | the funds themselves |
| `funding_instrument_sources.jsonl` | 980 | which event sources belong to which fund |
| `eligibility_gates.jsonl` | 7,471 | the encoded requirements — the thing at risk |
| `eligibility_clauses.jsonl` | 893 | obligations, cumulation, application, ticket |
| `instrument_application.jsonl` | 283 | how you apply |
| `MANIFEST.json` | — | counts, identities, sha256 per file, when and from where |

**Events are deliberately not here.** There are 311k of them, the volume is of
record for them, and no derived store has ever run ahead on them. A ledger big
enough to hold them would stop being read, which is the failure this guards
against.

Each line is one row as JSON, sorted by that table's identity, so a re-export
with no change produces an empty diff. Surrogate `id` columns are dropped
wherever the identity is not the id itself — a SQLite `AUTOINCREMENT` id is a
fact about one store's row numbering, not about the gate.

## Restoring

Restore is **insert-only**. It puts back rows the target does not have; it
never updates a row the target already has and it never deletes anything. So it
is safe to run against a healthy store — that is a no-op — and it is the right
thing to run against a store that has just lost rows.

```
# see what would come back, write nothing
python3 ETL/events/load/instrument_ledger.py restore --into data/db.sqlite --dry-run

# put them back
python3 ETL/events/load/instrument_ledger.py restore --into data/db.sqlite
```

To restore into the corpus of record, pull it to a sidecar first, restore into
the sidecar, and push that — never restore into a live file you have not copied:

```
python3 ETL/events/extract/pull_db_side.py /tmp/volume-db.sqlite
python3 ETL/events/load/instrument_ledger.py restore --into /tmp/volume-db.sqlite
```

If the target predates a migration, the restore says which columns it had no
room for and does not silently drop them in silence. Run `migrations/apply.py`
first and restore again.

## Keeping it current

```
python3 ETL/events/load/instrument_ledger.py export     # store -> ledger
python3 ETL/events/load/instrument_ledger.py verify     # ledger vs store, exit 1 on drift
```

Export after any encoding session, and **commit it**. An uncommitted ledger is
the same single copy the encoding already was.

`verify` is the honest check: it prints what each side holds alone. `only-store`
rows are work that has no committed copy yet.

## What this is not

Not a database backup — it holds five tables of ten thousand rows, not the
corpus. Not a source of truth — the store is; this is a record of what the store
held at a moment. Not a reconciler — to merge two *live* stores that have both
moved, use `ETL/events/load/reconcile_stores.py`, which merges by union and
never deletes.
